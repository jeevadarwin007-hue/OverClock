1. EXECUTIVE SUMMARY & PLATFORM MISSION
================================================================================
Higher education campuses operate in deep silos. When an air conditioner fails in
a smart classroom during a 110-student semester examination:
- Facilities submits a work order into a facilities tool.
- Academics does not know the room is unusable until students arrive sweating.
- Timetabling scrambles to relocate the exam manually, risking room clashes.
- Maintenance orders replacement circuit breakers without knowing they are out
  of stock, halting repairs for days.
- Department Deans have no visibility into the causal cascade of operational
  failures across physical blocks.

CampusOps solves this crisis by combining:
1. Neuro-Symbolic AI: Lightning-fast NLP extraction using Groq Cloud API
   (Llama-3.3-70b-versatile) with automatic fallback to deterministic regex.
2. Topological Consequence Engine: An explicit Directed Acyclic Graph (DAG) of
   all campus spaces, electrical buses, PoE switches, and HVAC lines.
3. Strict Database Invariants: PostgreSQL GiST exclusion constraints, 3-bucket
   inventory checks, and DAG cycle triggers that make double-bookings, stock
   drift, and cyclic loops mathematically impossible.
4. What-If Contingency Simulator: Dry-run causal simulation comparing Plan A
   (immediate room relocation) vs Plan B (examination cancellation) before any
   state mutation occurs.
5. Human-in-the-Loop Execution: Plans require authorized role-based approval
   with strict Separation of Duties before being executed in a single atomic
   PostgreSQL transaction.

THE CORE OPERATIONAL LOOP:
  SIMULATE (Read-Only) -> APPROVE (Human-in-the-Loop) -> EXECUTE (Revalidated Atomic Transaction) -> PROVE (Live Invariants)

3. ARCHITECTURAL INVARIANTS & NEURO-SYMBOLIC DIVIDE
================================================================================
CampusOps enforces strict boundaries between probabilistic AI and deterministic
business logic:

1. Neuro-Symbolic Isolation:
   - LLMs (Groq Llama-3.3-70b-versatile) are STRICTLY RESTRICTED to parsing
     unstructured text, extracting entity slots, stateful clarification, and
     generating campus pulse narrative summaries.
   - AI NEVER makes decisions regarding permissions, room scheduling, inventory
     reservations, technician assignments, budget approvals, or FSM transitions.
   - All deterministic logic is enforced by PostgreSQL constraints, triggers,
     and Python state machines.

2. Zero DB Locks During AI Inference:
   - External Groq API calls and embeddings run entirely outside PostgreSQL
     transactions. Database connections are checked out only after extraction.

3. Strict LLM Timeout & Deterministic Regex Fallback:
   - Every Groq API call enforces an asyncio.wait_for timeout of 2.5 seconds.
   - On timeout, rate limit (HTTP 429), malformed JSON, or network error, the
     system falls back seamlessly to fallback_parser.py (deterministic regex).
   - Zero unhandled 500 errors; zero invented room codes.

4. PostgreSQL-Enforced Physical Invariants:
   - Invariant 1 (Zero Double-Booking): Enforced via PostgreSQL GiST exclusion
     constraint on room_bookings using btree_gist:
       EXCLUDE USING gist (room_id WITH =, booking_window WITH &&)
     WHERE (status IN ('CONFIRMED', 'IN_PROGRESS', 'CONTINGENCY_HOLD'))
   - Invariant 2 (Three-Bucket Inventory Invariant):
       CHECK (physical_on_hand_qty = available_qty + reserved_qty)
       CHECK (physical_on_hand_qty >= 0 AND available_qty >= 0 AND reserved_qty >= 0)
     Guarantees that items cannot be allocated beyond warehouse reality.
   - Invariant 3 (Topological DAG Cycle Prevention):
       PL/pgSQL trigger check_campus_node_dag_cycle() walks parent-child edges
       using a recursive CTE and aborts cyclic inserts with SQLSTATE '23514'.
   - Invariant 4 (Cryptographic Tamper-Evident Audit Log):
       PL/pgSQL trigger enforce_audit_immutability() rejects any UPDATE or
       DELETE operation on audit_logs. Every row contains previous_hash and
       record_hash (SHA-256).
   - Invariant 5 (Row-Level Security Context):
       Database connections set transaction-local variables:
       SET LOCAL app.current_actor_id = '...';
       SET LOCAL app.current_actor_role = '...';
       SET LOCAL app.current_dept_id = '...';

4. BACKEND ARCHITECTURE & CORE SUBSYSTEMS
================================================================================
The backend is built with FastAPI and asyncpg, organized into clean modular domains:

1. Security & Authentication (backend/app/core/security.py):
   - Passwords hashed using Argon2id (passlib).
   - Stateless JWT tokens signed with HMAC-SHA256.
   - FastAPI dependencies: get_current_user, require_roles(['SYS_ADMIN', ...]).

2. Database Connection Pool (backend/app/database.py):
   - asyncpg connection pool with max 20 connections.
   - acquire_conn context manager that sets secure actor session variables on checkout.

3. Work Order FSM Engine (backend/app/modules/work_orders/):
   - Allowed States: INGESTED, AWAITING_CLARIFICATION, TRIAGED, ASSIGNED,
     IN_PROGRESS, BLOCKED_PARTS, PENDING_APPROVAL, APPROVED_READY, RESOLVED,
     CLOSED, CANCELLED, MERGED_DUPLICATE.
   - Enforces transition validation against the fsm_state_transitions table.
   - Guard rules:
     * Transition to IN_PROGRESS requires actor to be assigned tech or SYS_ADMIN.
     * Repairs exceeding ₹5,000 require an APPROVED record matching the snapshot hash.
     * Transition to RESOLVED requires resolution notes and zero pending parts.

4. Atomic Inventory Reservation (backend/app/modules/inventory/):
   - Multi-item reservation uses row-locking:
       SELECT * FROM inventory_items WHERE id = ANY(...) ORDER BY id ASC FOR UPDATE;
     (Ordering by ID prevents database deadlocks).
   - If available_qty < requested_qty, initiates automated PART_SHORTAGE cascade:
     * Work order transitions to BLOCKED_PARTS.
     * Emergency procurement requisition spawned in pending approvals.
     * Outbox event EM_PROCUREMENT_REQUESTED dispatched.

5. Staff Dispatch Scoring Engine (backend/app/modules/staffing/):
   - Deterministic multi-factor scoring formula:
       Score = (Skill_Match * 40) + (Workload_Score * 30) - (Distance_Penalty * 20) + (Shift_Weight * 10)
   - Anti-Flap Guard: Technicians cannot be reassigned more than 3 times within
     30 minutes without escalation to ESTATE_MANAGER.

6. Incident Intake & Multi-Turn Clarification (backend/app/modules/intake/):
   - Groq Cloud API Llama-3.3-70b-versatile with JSON schema response format.
   - Ambiguity Detection: If a user reports "lab on 3rd floor" when 3 labs exist,
     the ticket is placed into AWAITING_CLARIFICATION with partial slots saved.
   - Thread-Bound Slot Merging: Follow-up user responses on the same thread
     merge slots into the existing ticket without spawning duplicates.
   - Idempotency layer: SHA-256 request payload hashing rejects duplicate posts.

7. Two-Stage Topological Correlator (backend/app/modules/correlation/):
   - Stage A (Duplicate Suppression): Identical issues on the same node within
     15 minutes are merged into a master ticket (state = MERGED_DUPLICATE).
   - Stage B (Topological DAG Correlation): If >= 3 sibling nodes report
     failures within 10 minutes, the correlator traverses the DAG to find the
     common parent (e.g. switch SW-CORE-ACAD-F3) and spawns a P0 master ticket.

8. Constraint Satisfaction (CSP) Room Solver (backend/app/modules/scheduling/):
   - Finds clash-free rooms during disruptions.
   - Hard Constraints: capacity >= required, features @> required, room is
     operational, no GiST temporal overlap.
   - Soft Penalty Scoring: Same building (0 vs 20), floor delta (5 per floor),
     seat waste ((capacity - required) * 0.2).

9. What-If Simulator & Atomic Execution (backend/app/modules/simulation/):
   - Generates read-only simulation dry runs with Plan A vs Plan B trade-offs.
   - Execution revalidates state against concurrent changes, relocates bookings,
     reserves inventory, and dispatches staff inside a single atomic transaction.

10. Separation of Duties Approvals (backend/app/modules/approvals/):
    - Requester cannot approve their own requisition.
    - Financial thresholds: > ₹5,000 requires ESTATE_MANAGER; > ₹25,000 requires CAMPUS_DEAN.
    - Approvals verify SHA-256 canonical snapshot hash before authorizing execution.

11. Transactional Outbox Pattern (backend/app/workers/outbox_worker.py):
    - Events inserted into outbox_events in the same transaction as business data.
    - Asynchronous background worker polls and dispatches events with exponential backoff.

8. STEP-BY-STEP GUIDE: HOW TO RUN CAMPUSOPS
================================================================================

STEP 1: Verify PostgreSQL Database Connection
  Ensure your PostgreSQL database is running on localhost:5432 with database
  name 'campusops'. If you are using Docker:
    docker compose up -d postgres

  To verify connectivity in PowerShell:
    Test-NetConnection -ComputerName localhost -Port 5432

STEP 2: Run Database Schema Migrations and Seed Demo Data
  If setting up for the first time or re-initializing the database:
    # 1. Apply DDL (17 tables, triggers, constraints)
    python scripts/setup_db.py

    # 2. Seed SRM Easwari College topology, users, nodes, and fixtures
    python scripts/seed_demo.py

STEP 3: Start the FastAPI Backend Server
  Open a terminal window and navigate to the backend directory:
    cd a:\Projects\OverClock\backend
    python -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload

  Once started:
  - Backend API: http://localhost:8000
  - Interactive Swagger Docs: http://localhost:8000/docs
  - Health Endpoint: http://localhost:8000/health

STEP 4: Start the React Frontend Application
  Open a second terminal window and navigate to the frontend directory:
    cd a:\Projects\OverClock\frontend
    npm run dev

  Once Vite starts:
  - Open your browser and navigate to: http://localhost:5173

STEP 5: (Optional) Run the Asynchronous Outbox Worker
  To process outbox events in the background:
    cd a:\Projects\OverClock
    python -m backend.app.workers.outbox_worker

SCENARIO 1: AC Failure & 110-Student Exam Relocation Cascade
--------------------------------------------------------------------------------
The Problem:
  During an active autonomous semester exam in Room RM-ACAD-204 (110 students),
  the primary HVAC compressor suffers a severe electrical trip.
The Operational Flow:
  1. Intake: Natural language report received via Groq AI:
     "AC unit is smoking and making loud grinding noises in RM-ACAD-204."
  2. Consequence Trigger: Room RM-ACAD-204 is marked NON-OPERATIONAL.
  3. Exam Clash Detected: Active booking for 110 students immediately flagged
     as high disruption.
  4. What-If Simulator Invoked:
     - CSP solver searches for alternative rooms.
     - Hard constraints eliminate small classrooms.
     - Candidate found: RM-MECH-102 (PG Mechanical Block, capacity 125, operational).
     - Trade-off calculated: Plan A (Relocate, disruption score 12/100) vs
       Plan B (Cancel, disruption score 85/100).
  5. Contingency Hold: Room RM-MECH-102 placed on contingency hold.
  6. Part Shortage: Technician requests 63A breaker PART-MCCB-63A. Stock is 0.
     System triggers BLOCKED_PARTS and spawns emergency procurement requisition.
  7. Human-in-the-Loop Approval: Estate Manager reviews requisition and approves
     the ₹8,500 emergency order.
  8. Atomic Execution: Simulator executes Plan A; booking relocated, room locked,
     technician dispatched, zero double-booking violations.

--------------------------------------------------------------------------------
SCENARIO 2: Floor 3 Wi-Fi Storm Topological DAG Correlation
--------------------------------------------------------------------------------
The Problem:
  PoE Switch SW-CORE-ACAD-F3 crashes on Floor 3 of EEC-ACAD Block.
  Within 4 minutes, faculty and students submit separate reports:
  - Report 1: "Internet is completely down in LAB-ACAD-301"
  - Report 2: "Cannot connect to campus Wi-Fi in LAB-ACAD-302"
  - Report 3: "Wi-Fi access point showing red light in LAB-ACAD-304"
The Operational Flow:
  1. Stage A: Correlator confirms these are three distinct rooms (not duplicates).
  2. Stage B: Correlator traverses the campus DAG hierarchy:
     LAB-ACAD-301 -> SW-CORE-ACAD-F3
     LAB-ACAD-302 -> SW-CORE-ACAD-F3
