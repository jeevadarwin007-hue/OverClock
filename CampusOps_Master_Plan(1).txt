-------------------------------------------------------------
1. VISION AND PITCH
-------------------------------------------------------------
One-line pitch:
  CampusOps is a campus digital twin that shows the consequences of a
  failure before it happens, then executes the recovery with
  database-enforced guarantees.

Tagline:
  One Campus. One Operational Brain. Zero Disconnected Workflows.

Problem:
  Universities run on disconnected spreadsheets, chat groups and manual
  processes. This causes duplicate complaints, delayed maintenance,
  unavailable technicians, double-booked rooms, stock shortages and poor
  communication.

Solution:
  A unified platform that understands how campus resources relate to each
  other (buildings, rooms, assets, technicians, bookings, inventory,
  approvals) and coordinates the whole response to an incident.

Closing statement:
  "CampusOps doesn't just show you what broke. It shows you what happens
   next, and proves what it changed."

Three pillars:
  1. Campus Intelligence      - understand incidents (NLP, correlation).
  2. Autonomous Operations    - coordinate people, rooms, parts, approvals
                                through validated workflows.
  3. Predictive Decision Support - simulate impact, compare recovery plans,
                                and execute the chosen one safely.


-------------------------------------------------------------
2. CORE IDEA: SIMULATE -> APPROVE -> EXECUTE -> PROVE
-------------------------------------------------------------
1. SIMULATE (read-only)
   An administrator picks a disruption (room failure, technician leaves,
   part shortage, switch failure). The system walks the dependency graph
   and shows the full consequence cascade WITHOUT touching live data.

2. APPROVE
   The administrator compares Plan A and Plan B with reasons, SLA risk
   and conflicts, then selects one.

3. EXECUTE
   The chosen plan is revalidated against the current database state and
   committed in one transaction: booking change, work order, stock
   reservation, audit record, outbox notification. If the state changed
   since the simulation, the plan is rejected or refreshed.

4. PROVE
   An Invariant Panel shows live checks (no double bookings, stock
   balanced, audit intact, no duplicate events), plus the audit trail and
   notification history for what just changed.

Rule that ties everything together:
  Every visual shown must be backed by a guarantee that can be
  demonstrated.


-------------------------------------------------------------
3. DESIGN PRINCIPLES
-------------------------------------------------------------
1. Correctness before intelligence. Make the operational core reliable
   first, then add AI.
2. Integration before feature count. One incident correctly affecting
   rooms, exams, staff, inventory, approvals and notifications beats ten
   disconnected modules.
3. Evidence before claims. Concurrency tests, DB invariants and failure
   recovery are shown with real output.
4. AI assists, never decides. Authorization, scheduling, stock,
   approvals, state transitions, SLA math and plan execution are
   deterministic backend logic.
5. No fake data in the final demo. Every dashboard number comes from the
   database.
6. Modular monolith. No microservices, Kubernetes or Kafka.
7. A reliable simple feature beats an unreliable sophisticated one.

4. FUNCTIONAL MODULES
-------------------------------------------------------------
MODULE A - COMMAND CENTER
  Admin dashboard and main entry point.
  - Active incidents, critical/high alerts
  - Open work orders, blocked work orders
  - SLA compliance and deadline indicators
  - Technician availability
  - Inventory shortages
  - Room utilization, upcoming bookings
  - Recent activity and notifications
  - Campus Pulse: short natural-language summary of current state.
    Facts and numbers come from the database; the LLM only phrases them
    and must not invent statistics.
    Example: "Campus operations are stable. Three requests need
    attention. One classroom is unavailable due to an electrical issue.
    Two work orders are awaiting spare parts."

MODULE B - AI INCIDENT INTELLIGENCE
  - Intake: structured form, natural-language chat, simulated email or
    webhook.
  - Extraction: category, location, asset, urgency, description, related
    event (for example an exam).
  - Clarification: if location or asset is missing or ambiguous, ask.
    Never invent missing information. Use a conversation thread with
    persisted partial slots; do not create a new ticket per reply.
  - Categorization: electrical, plumbing, network, furniture, classroom
    equipment, cleaning, building maintenance, safety.
  - Duplicate detection: combine exact asset match, room match, category,
    time window, text similarity and infrastructure dependency.
    Do not auto-merge on text similarity alone. Explain the evidence and
    let authorized users confirm uncertain cases.
  - Correlation: group related reports under a parent (master) incident
    while preserving every original report.
  - Incident briefing: what happened, where, affected resources, related
    incidents, consequences, suggested next steps - grounded in database
    records.

MODULE C - WORKFORCE
  - Technician profiles: skills with proficiency, shift, availability,
    leave, workload, assignment history, contact.
  - Deterministic assignment scoring with explanation.
  - Dynamic reassignment when a technician becomes unavailable, with full
    history (never silently overwrite).

MODULE D - SPACE AND ASSETS
  - Rooms: number, building, floor, capacity, type, features,
    accessibility, operational status.
  - Bookings: classes, exams, faculty reservations, events, maintenance
    blocks.
  - Double-booking prevention enforced by the database.
  - Impact-aware alternative room recommendations.
  - Assets: projectors, computers, AC, electrical panels, network
    switches, access points, lab equipment, furniture. Each linked to a
    room, maintenance history and incidents.

MODULE E - INVENTORY AND PROCUREMENT
  - Parts with available, reserved and minimum quantities.
  - Reservation per work order; no overselling.
  - Missing part -> work order BLOCKED -> procurement request ->
    approval -> receipt -> revalidation -> work resumes.

MODULE F - WHAT-IF SIMULATOR (signature demo feature)
  - Scenarios: room unavailable, technician unavailable, part shortage,
    Wi-Fi switch failure, power outage, multiple simultaneous
    disruptions.
  - Read-only impact analysis, plan generation and comparison.
  - Authorized execution with full revalidation.

5. CAMPUS DIGITAL TWIN AND MAP
-------------------------------------------------------------
Two linked representations:

(a) Geographic / schematic map (Campus Explorer)
  - Based on the KARE campus layout (verify against the official master
    plan in the university's 2024-25 sustainability report before use).
  - Practical approach: a simplified schematic or GeoJSON of verified
    buildings, drawn with MapLibre GL JS (via react-map-gl), with
    OpenStreetMap raster tiles where useful. Label anything unverified
    as demo data.
  - Clickable buildings; selecting one shows rooms, equipment, active
    incidents, open work orders, upcoming bookings, asset history and
    responsible technicians.
  - Incident markers, asset status indicators, room availability.
  - Filters by incident type, severity and building.
  - Navigation from a map selection to detailed records.
  - Use clear status indicators, not decorative graphics.

(b) Infrastructure dependency graph (in PostgreSQL)
  Example:
    Building
      +-- Main electrical substation
      |     +-- Floor 1 breaker -> Rooms 101, 102
      |     +-- Floor 2 breaker -> Rooms 201, 202
      +-- Network
            +-- Core switch
                  +-- Switch A -> Lab 101, Lab 102
                  +-- Switch B -> Lab 201

  Tables:
    campus_nodes: id, node_code, name, node_type, building_code,
                  floor_number, room_capacity, room_features,
                  is_operational, criticality_weight
    node_dependencies: parent_node_id, child_node_id, dependency_domain
  Rules:
    - Validate acyclicity on writes; serialize graph mutations.
    - Use visited-node guards in traversals.
    - Preserve dependency domain (power, network, water, ...).

(c) 2.5D CAMPUS VIEW (MANDATORY)
  The Campus Explorer must provide a 2.5D view: the same building
  footprints rendered as extruded blocks (MapLibre fill-extrusion), not
  full 3D models.
  - Data: GeoJSON footprint per building with properties building_code,
    name, floors, height_m. Height = floors x about 3.5 m. Use verified
    floor counts where available; otherwise mark heights as approximate
    demo data in the UI.
  - Status coloring: each block is colored from live backend data
    (normal, active incident, blocked work order, room unavailable),
    served by GET /api/v1/campus/map-status. Colors must never be
    hardcoded.
  - Interaction: tilt and rotate; click a building to open the same
    detail panel as the 2D view (rooms, assets, incidents, work orders,
    bookings, technicians); incident markers and map highlights from the
    consequence graph and simulator (affected buildings pulse or
    highlight).
  - 2D / 2.5D toggle with a status legend. The 2D mode is the fallback
    if WebGL is unavailable.
  - Simulator integration: when a dry run is open, affected buildings
    and rooms are highlighted in the 2.5D view (clearly marked as
    "simulated", not live).
  - Keep it functional: no decorative animation, no fake data, no
    interior 3D models.

Stretch: simplified indoor SVG floor plans for one or two buildings.

6. EXPLAINABLE CONSEQUENCE GRAPH (SIGNATURE FEATURE)
-------------------------------------------------------------
When an incident occurs or a simulation runs, show how one failure
cascades:

  Electrical panel fault
   -> Room A201 unavailable
       -> Examination (120 students, 10:00) affected
       -> Maintenance work order created
            -> Technician unavailable -> reassignment recommended
            -> Part out of stock -> work order BLOCKED
                 -> Procurement request -> approval pending
       -> Faculty notified

Requirements:
  - Rendered with React Flow, linked to map highlights.
  - Each edge/node is clickable and shows: evidence (database records),
    current status, and the rule that produced it.
  - Built from real queries over the dependency graph, bookings, work
    orders, stock and approvals. Nothing hardcoded.
  - The same engine powers both live incident impact and the simulator
    (simulator runs it in dry-run mode).


-------------------------------------------------------------
7. AI LAYER
-------------------------------------------------------------
AI MAY:
  - Extract issue details; suggest category and urgency
  - Generate incident summaries and Campus Pulse wording
  - Suggest possible duplicates and explain evidence
  - Draft clarification questions
  - Recommend possible next actions

AI MUST NOT:
  - Authorize purchases or approve repairs
  - Override inventory or bypass booking conflicts
  - Change permissions
  - Mark work as resolved
  - Make any permission, scheduling or stock decision

Safeguards:
  - All extracted entities validated against real campus records.
  - Short LLM timeout (initially 2.5 s). On timeout or invalid output use
    a deterministic regex/keyword fallback parser. Never invent missing
    room, asset or urgency.
  - Treat all external text (emails, chat) as untrusted; defend against
    prompt injection; never let model output call privileged operations
    directly.
  - Provider abstraction so the LLM (for example Gemini) is replaceable.
  - Do not present example confidence numbers as measured results.
  - Manual complaint form always available if AI fails.

Clarification flow:
  INGESTED -> AWAITING_CLARIFICATION -> (user replies; merge slots into
  the same thread) -> validate entity -> TRIAGED

Correlation policy:
  - Exact asset/room + same category + time window: duplicate candidate.
  - High similarity with supporting evidence: strong correlation
    candidate.
  - Medium similarity: ask a human to confirm.
  - Low similarity: keep separate.
  - Never merge unrelated issues merely because they mention the same
    room. Always preserve original reports.

8. TECHNOLOGY STACK
-------------------------------------------------------------
Frontend: React, TypeScript, Vite, Tailwind CSS, shadcn/ui, React Router,
          TanStack Query, MapLibre GL JS (react-map-gl) for the 2D and
          2.5D campus map, React Flow (xyflow), Recharts, Lucide icons.
Backend:  Python 3.12, FastAPI, Pydantic, SQLAlchemy (or asyncpg),
          Alembic, HTTPX, pytest, pytest-asyncio.
Database: PostgreSQL with btree_gist; pgcrypto if needed; pgvector only
          if semantic search is implemented in the database.
AI:       Structured-output LLM API + deterministic fallback; optional
          sentence-embedding model.
Infra:    Docker Compose. Environment variables for all secrets.

Avoid: Kubernetes, Kafka, Redis, microservices, multi-agent AI
architectures, blockchain audit logs, full 3D building models or
interior 3D (the 2.5D extruded map in section 5 is required).


-------------------------------------------------------------
9. ARCHITECTURE AND TRANSACTION BOUNDARIES
-------------------------------------------------------------
Layers:
  1. Intake and AI: forms, chat, email/webhook, extraction, clarification.
  2. Digital twin and correlation: campus graph, impact, grouping.
  3. Deterministic operations engine: FSM, assignment, booking,
     inventory, approvals, SLA, notifications.
  4. PostgreSQL invariant kernel: constraints, transactions, audit,
     idempotency, outbox.

Request path:
  HTTP request -> route -> authentication/authorization -> domain service
  -> transaction boundary -> repository/PostgreSQL.
  Routes contain no business logic.

Complaint data flow:
  1. Authenticate request; claim idempotency key.
  2. AI extraction OUTSIDE any operational DB transaction.
  3. Validate extracted entities against campus records.
  4. Ask for clarification if fields are missing/ambiguous.
  5. Correlate with existing incidents.
  6. Assess downstream impact (consequence engine).
  7. Short atomic transaction: revalidate constraints and commit work
     order, booking, inventory and audit changes.
  8. Write notification intents to the transactional outbox in the same
     transaction.
  9. Deliver notifications asynchronously.
 10. Analytics read from persisted records.

Transaction rules:
  - Never hold DB locks while waiting for the LLM, a human or email.
  - Sort part IDs before locking multiple inventory rows.
  - Keep transactions short and bounded.


-------------------------------------------------------------
10. DATABASE DESIGN AND INVARIANTS
-------------------------------------------------------------
Use normalized relational tables, foreign keys, indexes and constraints.
No single generic table, no unstructured JSON database.

Identity and access:
  users, departments, roles, permissions, role_assignments,
  staff_skills, staff_shifts, staff_leave_blocks
Campus:
  campus_nodes, node_dependencies, room_features, assets,
  maintenance_history
Incidents and workflow:
  incident_reports, incidents (master/parent), incident_relationships,
  conversation_threads, work_orders, work_order_assignments,
  assignment_history, fsm_state_transitions (status history)
Scheduling:
  room_bookings, room_booking_impacts, room_relocations
Inventory and procurement:
  inventory_parts, inventory_movements, part_reservations,
  purchase_requests, purchase_request_items, approvals, suppliers,
  goods_receipts
Reliability and security:
  processed_events, audit_logs, outbound_notifications
SLA:
  sla_policies, sla_events, escalations
Simulation:
  simulation_runs, simulation_actions (stored plans; no live mutation)

Critical invariants (must be enforced in the database or in a single
transaction, never only in the UI):
  - No overlapping active bookings: GiST exclusion constraint
      EXCLUDE USING gist (room_node_id WITH =, time_slot WITH &&)
    on active booking states; finite, non-empty, half-open [) ranges.
  - No negative inventory: CHECK constraints.
  - Stock conservation: physical = available + reserved (CHECK).
  - Every stock movement inserted in the same transaction as the
    balance update.
  - No graph cycles: validated and serialized on write.
  - No invalid state transitions: controlled transition function.
  - No self-approval: policy plus constraint/service check.
  - No duplicate event processing: unique idempotency key, atomic claim.
  - Audit log append-only for ordinary application roles.
  - No lost notification intent: transactional outbox.

Security note (document honestly): custom session variables and
caller-supplied roles are not proof of identity; a database superuser can
bypass ordinary protections. Do not claim protection beyond the controls
actually implemented.


-------------------------------------------------------------
11. WORK-ORDER STATE MACHINE
-------------------------------------------------------------
Core states (MVP):
  OPEN -> ASSIGNED -> IN_PROGRESS -> COMPLETED
  IN_PROGRESS -> BLOCKED (missing part or other blocking condition)
  BLOCKED -> ASSIGNED or IN_PROGRESS (after blocker resolved)
  Cancellation/rejection with reason and permission.

Extended states (use if time allows, from the blueprint):
  INGESTED, AWAITING_CLARIFICATION, TRIAGED, MERGED_DUPLICATE,
  BLOCKED_PARTS, PENDING_APPROVAL, APPROVED_READY, RESOLVED, CLOSED,
  ESCALATED_SAFETY_REVIEW.

Every transition requires:
  current state, requested state, authenticated actor, authorized role,
  preconditions (assignment, stock reservation, approval validity,
  safety), a reason, and an audit record storing previous state, new
  state, user, timestamp and relevant conditions.

No generic "update status" endpoint. All changes go through the
transition service.


-------------------------------------------------------------
12. INVENTORY, APPROVALS AND PROCUREMENT
-------------------------------------------------------------
Part reservation:
  1. Check available stock.
  2. Reserve quantity in a transaction (row locks, ordered by part ID).
  3. Link reservation to the work order.
  4. Prevent other work orders from taking the same stock.
  5. Record a stock movement.

Example accounting:
  Start: physical 10, available 10, reserved 0
  Reserve 3 -> available 7, reserved 3
  Release 1 -> available 8, reserved 2
  Consume 2 -> physical 8, available 8, reserved 0

Part unavailable:
  - Mark work order BLOCKED, record missing part and quantity.
  - Create a procurement request.
  - Show affected work orders and operational impact.
  - Notify the right people.

Approvals (configurable demo policy, fictional):
  - Rs. 0 - 5,000: Department Manager
  - Rs. 5,001 - 25,000: Facilities Administrator
  - Above Rs. 25,000: Procurement Approver

Enforce: approver role and authority, spending limit, no self-approval
(requester, reporter or assigned technician cannot approve their own
request), separation of duties.

Receipt:
  When the part arrives: update inventory, record movement, revalidate
  reservation, make the blocked work order eligible to resume, notify the
  technician.

Stretch: SHA-256 snapshot of the material approval fields; recompute at
approval and execution, invalidate if changed. (Integrity evidence, not a
replacement for authorization.)

Deferred: budget encumbrance accounting
  (Total = Available + Encumbered + Spent).


-------------------------------------------------------------
13. ROOM SCHEDULING AND ALTERNATIVES
-------------------------------------------------------------
Booking types: class, exam, faculty reservation, event, maintenance
block.

Double-booking prevention: GiST exclusion constraint plus transactional
validation in the service; the frontend check is only a convenience.

When a room becomes unavailable:
  1. Mark it non-operational (authorized operation).
  2. Find affected bookings (classes, exams).
  3. Preserve the original booking records.
  4. Flag bookings as needing relocation.
  5. Search alternatives by HARD constraints:
       capacity >= required, required features present, time slot free,
       room operational, accessibility satisfied.
  6. Rank viable alternatives (for example capacity fit, proximity,
     feature match) and give reasons for each.
  7. Reserve an alternative only after successful booking, after admin
     approval.
  8. Escalate if no valid alternative exists.
  Never claim a relocation succeeded just because a room was suggested.


-------------------------------------------------------------
14. TECHNICIAN ASSIGNMENT
-------------------------------------------------------------
Eligibility (hard filters): required skill, on shift (including overnight
shifts), not on leave, available.

Score (configurable weights, initial values):
  35% skill suitability
  25% availability
  20% workload suitability
  20% priority / SLA suitability

Each recommendation includes a plain-language explanation, for example:
  "Technician A has the required electrical skill, is on shift and has a
   lower workload than other eligible technicians."

Dynamic reassignment:
  detect availability change -> find affected assignments -> recompute
  eligible technicians -> recommend -> revalidate -> record in assignment
  history -> notify. Never silently overwrite earlier assignments.
  Revalidate eligibility at commit time; escalate if nobody is eligible.


-------------------------------------------------------------
15. SIMULATOR (DRY RUN AND EXECUTE)
-------------------------------------------------------------
Inputs: scenario type, target (room, technician, part, switch), time,
event description.

Dry run (never mutates live state):
  - Affected bookings, classes, exams and headcount
  - Installed assets and dependent nodes
  - Related work orders and required technicians
  - Possible part needs
  - SLA risk
  - Available alternative rooms
  Output: one or more recovery plans.

Example plans for "classroom unavailable before exam":
  Plan A: move exam to a compatible available room.
  Plan B: repair in time, if technician, parts and time allow.
  Compare: time required, resource availability, conflicts, operational
  impact, SLA consequences, cost only if reliable data exists.

Storage: simulation_runs and simulation_actions hold the proposed plan
with a snapshot version/timestamp.

Execute:
  1. Check authorization.
  2. Revalidate room availability.
  3. Revalidate technician availability.
  4. Revalidate inventory.
  5. Revalidate approval requirements.
  6. Revalidate booking conflicts.
  7. Execute permitted operations in one transaction.
  8. Write audit records.
  9. Queue notifications.
  If conditions changed since simulation: reject or recompute the plan
  and tell the user why.

16. ROLES AND ACCESS CONTROL
-------------------------------------------------------------
Backend-enforced RBAC. Frontend visibility is convenience only.

Roles:
  1. Student / Faculty: submit and track own requests, view permitted
     room availability, request bookings where authorized, receive
     notifications.
  2. Technician: view assigned work, update progress, record findings,
     request parts, mark work blocked.
  3. Department Manager: review department incidents, assign/reassign,
     monitor technicians, approve department-level items.
  4. Facilities Administrator: campus-wide view, manage incidents, work
     orders, rooms and assets, review conflicts, run simulations,
     approve permitted changes.
  5. Procurement Approver: review and approve/reject purchase requests.
  6. System Administrator: manage users, roles, settings, master data,
     audit review.

Example permissions:
  work_order:create, work_order:read:own, work_order:read:department,
  work_order:read:all, work_order:assign, work_order:update,
  work_order:resolve, room:create_booking, room:cancel_booking,
  room:block, inventory:view, inventory:reserve, inventory:receive,
  approval:request, approval:approve, approval:reject,
  simulation:run, simulation:execute, system:manage_users,
  system:manage_roles

Security requirements:
  - Password hashing with Argon2id (library defaults are fine).
  - Short-lived access tokens plus refresh tokens.
  - Authorization checked on every protected endpoint.
  - Pydantic validation on all inputs.
  - Parameterized queries only.
  - Rate limiting on public intake.
  - Webhook signature verification.
  - Secrets only in environment variables; never in frontend code.
  - Audit all sensitive operations.

17. RELIABILITY, IDEMPOTENCY AND NOTIFICATIONS
-------------------------------------------------------------
processed_events fields:
  source, idempotency_key, payload_hash, status, attempt_count,
  claimed_at, lease_expires_at, response_status, response_payload.
  Stretch: worker_id and fencing token.

Behavior:
  - Same key + same payload: return stored result (or safe in-progress
    response).
  - Same key + different payload: reject.
  - Completed event: no repeated side effects.
  - Expired lease: safe reclamation (stretch).
  - Bounded retries; explicit failure states.

Transactional outbox:
  PENDING -> PROCESSING -> DELIVERED
  PENDING -> PROCESSING -> RETRY -> DEAD_LETTER
  Stable notification IDs; assume at-least-once delivery; do not mark
  SENT merely because it was queued. A background worker delivers and
  retries.

Simulated external integration (at least one):
  Email inbox / webhook endpoint. Example event:
    { "event_id": "EMAIL-1001",
      "sender": "faculty@campus.edu",
      "subject": "WiFi unavailable",
      "body": "Internet is not working in Lab 201",
      "received_at": "2026-10-30T09:00:00Z" }
  Flow: verify signature -> validate -> claim idempotency key -> intake
  -> persist records -> queue notifications.

AI failure fallback: deterministic parser plus manual form.

20. FRONTEND INFORMATION ARCHITECTURE AND VISUAL DESIGN
-------------------------------------------------------------
Navigation (role-aware):
  1. Overview (Command Center + Campus Pulse)
  2. Incidents (with relationship view)
  3. Campus Explorer (map)
  4. Work Orders
  5. Workforce
  6. Space and Scheduling
  7. Inventory and Procurement (approvals)
  8. What-if Simulator
  9. Analytics / SLA
 10. Audit and Invariants
 11. Administration

Incident workspace shows: details, original reports, AI summary,
correlation evidence, impacted rooms, related equipment, assigned
technician, inventory needs, SLA countdown, audit timeline.

Visual direction:
  - Deep navy navigation; white/off-white background; muted blue accent;
    neutral gray borders; restrained status colors.
  - Inter or Geist typography; consistent spacing; subtle shadows;
    8-12 px radii.
  - Looks like a professional enterprise operations product.
  Avoid: gradient "AI" backgrounds, oversized headings, excessive
  animation, decorative 3D models (the 2.5D map is functional and

22. DEMONSTRATION SCENARIOS
-------------------------------------------------------------
Both scenarios must run real backend workflows on persistent data.

SCENARIO 1 - EXAM ROOM FAILURE WITH STAFF AND PARTS PROBLEMS
Initial conditions (fictional demo values):
  - Exam in Room A201 (or C204), 55-120 students, starts in 60 min.
  - Electrical failure makes the room unavailable.
  - Candidate rooms: one too small, one occupied until after the exam
    starts, one with enough capacity and free.
  - First assigned technician becomes unavailable.
  - Required electrical part is out of stock.
Flow:
  1. Faculty submits the complaint (chat or form).
  2. AI extracts room, issue, urgency; entities validated.
  3. System identifies installed assets and the affected exam.
  4. Work order created; room marked non-operational by an authorized
     user.
  5. Map highlights the room; consequence graph shows the cascade.
  6. Simulator runs a dry run: affected students/exam, alternative
     rooms, Plan A vs Plan B.
  7. Too-small and occupied rooms rejected with reasons; suitable room
     recommended.
  8. Administrator approves; booking updated transactionally.
  9. Faculty notified; audit written.
 10. Technician unavailable -> reassignment recommended with explanation.
 11. Part reservation fails -> work order BLOCKED -> procurement request.
 12. Authorized approver approves (self-approval attempt rejected).
 13. Part received -> inventory updated -> work order resumes ->
     technician notified.
 14. SLA and audit updated.
Success: exam relocation correctly recorded; unresolved repair stays
visible as BLOCKED; nothing falsely marked resolved.

SCENARIO 2 - WI-FI OUTAGE (AI SHOWCASE)
Initial conditions:
  - Twelve reports from three computer labs in one building (chat and
    simulated email).
  - A common switch is the likely cause.
  - One network technician unavailable; replacement equipment out of
    stock.
Flow:
  1. Inject reports through chat and the email webhook.
  2. Extract locations and categories; flag duplicates/related.
  3. Find the common upstream node where evidence supports it.
  4. Create or associate a master incident; preserve all 12 reports.
  5. Affected labs light up on the map.
  6. Assign an eligible network technician or escalate.
  7. Detect stock shortage -> block dependent work.
  8. Update SLA; send targeted notifications.
  9. Replay an identical webhook live -> zero duplicate side effects.
Success: one correlated incident, twelve preserved reports, accurate
resource state, no false resolution.

OPTIONAL: other simulator scenarios (power outage, multiple
simultaneous disruptions).

23. TEST AND EVIDENCE PLAN
-------------------------------------------------------------
Use pytest and pytest-asyncio against a REAL PostgreSQL instance with
independent connections (not SQLite, not a shared session, not
sequential calls). Coordinate starts with asyncio.Barrier or similar.

Priority tests (run and show real output in the demo):
  1. 100 concurrent overlapping bookings for one room -> exactly 1
     succeeds.
  2. 100 concurrent reservations of the last part -> no overselling.
  3. 50 duplicate webhook deliveries -> one set of side effects.
  4. Same idempotency key, changed payload -> rejected.
  5. Invalid FSM transition -> rejected.
  6. Self-approval attempt -> rejected.
  7. Unauthorized approval API call -> rejected.
  8. Technician outside shift -> assignment rejected.
  9. LLM timeout -> deterministic fallback used.
 10. Simulation never changes live tables (row counts/checksums equal
     before and after a dry run).
 11. Stale plan execution (state changed after simulation) -> rejected
     or refreshed.
 12. Unrelated reports about the same room remain separate.

Additional if time permits:
  circular dependency insertion rejected; notification service down ->
  retry and recovery; worker crash lease recovery; audit tampering
  attempt rejected for ordinary roles; DB restart persistence.

Principles:
  - Query database invariants after tests.
  - Record failures, retries and duration.
  - Generate a machine-readable report plus a human-readable summary.
  - NEVER fabricate test results.
  - verify_invariants script exposes the same checks shown in the UI
    Invariant Panel.

28. RULES FOR AI CODING TOOLS
-------------------------------------------------------------
Treat this document as the primary specification.

Understand before implementing:
  - Do not turn the project into a generic college management system,
    complaint portal or chatbot.
  - Preserve the three pillars and the Simulate -> Approve -> Execute ->
    Prove loop.

Build functional features:
  - Every major screen connects to real backend functionality.
  - No hardcoded dashboard numbers, no do-nothing buttons, no
    frontend-only simulation of database success.
  - Do not call a feature complete if it is only a mockup.

Maintain architecture:
  - TypeScript frontend, FastAPI backend, PostgreSQL persistence,
    Alembic migrations, Pydantic validation, consistent error handling,
    maintained API docs.

AI must not control critical decisions (see section 7).

Work incrementally:
  1. Inspect the repository; never assume a file or feature exists.
  2. Understand relevant models and APIs.
  3. Plan, then implement one phase at a time.
  4. Write tests alongside business logic; run them after meaningful
     changes.
  5. Integrate the frontend only after the backend logic works.
  6. Verify the whole workflow (persistence, authorization, validation,
     errors, notifications).
  7. Do not rewrite working modules without justification.
  8. Do not modify unrelated features.
  9. Keep AI calls outside critical database transactions.
 10. Never rely on frontend-only permissions.
 11. Explain architectural decisions and trade-offs.
 12. Report incomplete features honestly and never fabricate test
     results.
 13. Maintain an implementation status file.

32. RISKS AND MITIGATIONS
-------------------------------------------------------------
Risk: Scope too large for four students.
  Mitigation: strict MUST SHIP list; stretch items only after the two
  scenarios pass.

Risk: Real campus map data is hard to verify.
  Mitigation: use a simplified schematic of verified buildings; label
  everything else as demo data; do not block other work on the map.

Risk: 2.5D map takes longer than planned or building footprints are
      inaccurate.
  Mitigation: build the 2D map and map-status endpoint first, then add
  extrusion as a layer over the same GeoJSON (small incremental step);
  use approximate heights labelled as demo data; keep the 2D mode as
  fallback.

Risk: Backend correct but demo looks plain.
  Mitigation: map, consequence graph and simulator are core MUST SHIP
  items, not polish.

Risk: Pretty UI over shallow logic.
  Mitigation: acceptance rule that no feature is "done" until its full
  workflow works with persistence, authorization and tests.

Risk: LLM latency, errors or prompt injection.
  Mitigation: timeout, fallback parser, entity validation, AI never
  calls privileged operations, manual intake form.

Risk: Integration problems between members.
  Mitigation: early API contracts, daily integration check, shared seed
  data, one demo environment.

Risk: Overclaiming security or test coverage.
  Mitigation: document actual controls only; show real test output; keep
  a known-defects list.

Final reminder:
  Do not confuse an architecture proposal with an implementation, a
  passing unit test with concurrency proof, or a polished demo with
  operational correctness. Build a defensible, working CampusOps.
